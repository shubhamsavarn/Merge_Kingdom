### 1.1 Client Clock Authority & Untrusted Timestamping
* **Evidence**:
  * Fact 2, `SaveSystem.Save()`, line:
    ```csharp
    Current.saved_at = DateTimeOffset.Now.ToUnixTimeSeconds();
    ```
  * Fact 1, footnote:
    `"saved_at is the time of the save, in seconds, from the phone clock."`
* **Impact on Version 2.5**:
  Timestamps generated by client phone clocks are completely untrusted. They are susceptible to accidental drift, timezone hopping, airplane-mode latency, and deliberate client-side time-travel exploits (e.g., date-skipping for free chests). Relying on client-reported wall-clock time as a monotonic ordering key is the primary root cause of data loss in the current game.

---

### 1.2 Blind Last-Write-Wins (LWW) Monolithic Overwrites
* **Evidence**:
  * Fact 3, Paragraph 1:
    `"The server keeps one save for each player. When an upload arrives, the server keeps it only if its saved_at is larger than the stored saved_at. The server does not read the other fields."`
  * Fact 2, `SaveSystem.OnCloudSave(string serverJson)`:
    ```csharp
    SaveData server = JsonUtility.FromJson<SaveData>(serverJson);
    if (server.saved_at > Current.saved_at) {
        Current = server;
        File.WriteAllText(LocalPath, serverJson);
    }
    ```
* **Impact on Version 2.5**:
  * The server operates as a dumb string-blob store. It has zero field awareness and performs no semantic validation or conflict resolution.
  * Because the conflict check is coarse-grained across the entire save blob (`server.saved_at > Current.saved_at`), an update to one domain (e.g., playing a level on Device A) completely overwrites changes in another domain (e.g., purchasing currency or no-ads on Device B).

---

### 1.3 Asynchronous Offline Queuing Flushes
* **Evidence**:
  * Fact 3, Paragraph 3:
    `"When a device is offline, CloudSync.Upload keeps the upload in a queue and sends it when the device is online again."`
  * Fact 2, `SaveSystem.Save()`:
    ```csharp
    CloudSync.Upload(json);
    ```
* **Impact on Version 2.5**:
  A save payload generated while offline preserves its original `saved_at` timestamp. When network connectivity is restored hours or days later, the queued payload is pushed. If its timestamp is higher than the server's current state, it blindly overwrites newer gameplay progress made on another device. Conversely, if its timestamp is lower, the server sends back its stored save, obliterating all offline progress made on the reconnecting device.

---

### 1.4 Asymmetric Purchase & Spend Visibility (The Currency Accounting Gap)
* **Evidence**:
  * Fact 4:
    `"The server has a record of each coin pack that a player bought: player, pack, number of coins, time. The server has no record of how players spent coins. Coins are spent on the phone."`
  * Fact 2, `SaveData`:
    ```csharp
    public int coins;
    ```
* **Impact on Version 2.5**:
  The system holds an aggregated balance of `coins` on the client, while the server only records credit transactions (IAP coin pack purchases). Because debit transactions (sinks: powerups, continues) are executed locally on the client without an audit ledger, **it is impossible to know mathematically whether a player's remaining coins were earned via puzzle gameplay or purchased with fiat currency**. The currency split algorithm must explicitly resolve this ambiguity.

---

### 1.5 Strict Deserialization Data Loss via Unity `JsonUtility`
* **Evidence**:
  * Fact 2, `SaveSystem.Load()` & `SaveSystem.OnCloudSave()`:
    ```csharp
    Current = JsonUtility.FromJson<SaveData>(json);
    string json = JsonUtility.ToJson(Current);
    ```
* **Impact on Version 2.5**:
  Unity's built-in `JsonUtility` drops any JSON keys not declared as public/serializable fields in the target C# class. If a v2.5 client or server introduces `public int gems;`, and that JSON payload is received by an older client (`v2.2`, `v2.3`, or `v2.4`), `JsonUtility` will silently discard the `"gems"` key. When that older client subsequently calls `Save()`, it serializes `SaveData` *without* `"gems"`, and its upload will permanently erase the player's gems on the server if the server remains a dumb LWW blob store!

### Incident 1: "Where did my levels go?" (Tablet vs. Airplane Mode Phone)
> *"I played on my tablet all weekend and got to level 160. My son played on my old phone in airplane mode on Sunday night, after I stopped. Today I am back at level 151. Where did my levels go?"*

```
Timeline: Incident 1 (Race Condition via Offline Queue Flush)
======================================================================================
Tablet (Online)                 Server                          Old Phone (Airplane)
======================================================================================
Sun Afternoon:
Plays to Level 160
SaveSystem.Save()
saved_at = T_tablet (Sun 18:00)
Uploads to server ────────────> Stores Level 160
                                (saved_at = Sun 18:00)
                                                                Sun Night (Airplane Mode):
                                                                Son plays: Level 150 -> 151
                                                                SaveSystem.Save()
                                                                saved_at = T_phone (Sun 21:00)
                                                                CloudSync queues upload (Offline)
Monday Morning:
                                                                Airplane mode turned OFF.
                                <────────────────────────────── Queued upload flushes:
                                                                Level 151, saved_at = Sun 21:00
                                Evaluates LWW:
                                Sun 21:00 > Sun 18:00 (TRUE)
                                Blindly overwrites server save:
                                Level = 151
Receives push:                  Pushes Level 151 save
OnCloudSave(serverJson) <────── to other devices
Evaluates:
Sun 21:00 > Sun 18:00 (TRUE)

```

#### Step-by-Step Technical Breakdown:
1. **Weekend (Tablet, Online)**: The player advances from level 150 to 160. On finishing level 160 on Sunday afternoon ($T_{tablet} = \text{Sunday 18:00:00}$), `SaveSystem.Save()` sets `Current.saved_at = 1761700000` ($T_{tablet}$) and calls `CloudSync.Upload(json)`.
2. **Server Storage**: The server receives the tablet's save. Because $T_{tablet} > \text{stored } saved\_at$, the server updates its record to `level: 160, saved_at: 1761700000`.
3. **Sunday Night (Old Phone, Offline in Airplane Mode)**: The son opens the game on the old phone. The phone's local cache is still at level 150. The son plays one level, reaching level 151 at Sunday night ($T_{phone} = \text{Sunday 21:00:00} = 1761710800$).
4. **Offline Queueing**: On level completion, `SaveSystem.Save()` runs on the old phone. `Current.saved_at` is stamped with the phone's clock ($T_{phone} = 1761710800$). Because the phone is in airplane mode, `CloudSync.Upload` retains this payload in its local persistent queue (Fact 3, bullet 3). Notice: **$T_{phone} > T_{tablet}$ by 3 hours**.
5. **Monday Morning (Old Phone Reconnects)**: Airplane mode is toggled off. `CloudSync` flushes its queue and transmits the save (`level: 151, saved_at: 1761710800`) to the server.
6. **Server Overwrite**: The server compares incoming `saved_at` ($1761710800$) against stored `saved_at` ($1761700000$). Per Fact 3, bullet 1: *"the server keeps it only if its saved_at is larger than the stored saved_at. The server does not read the other fields."* The server blindly accepts the old phone's payload and drops level 160.
7. **Tablet Overwrite**: Per Fact 3, bullet 2, the server broadcasts the new save to the tablet. On the tablet, `SaveSystem.OnCloudSave` triggers. Because $server.saved\_at (1761710800) > Current.saved\_at (1761700000)$, the tablet replaces its local save with `level: 151`. Nine levels of weekend puzzle progress are destroyed.

### Incident 2: "Those levels were gone" (Date Manipulation / Time-Travel Poisoning)
> *"I changed the date on my phone to tomorrow, opened the free chest early and played one level. Then I changed the date back. Later I played more levels on the bus with no internet. When I got home, those levels were gone."*

```
Timeline: Incident 2 (Timestamp Poisoning via Clock Tampering)
======================================================================================
Client Device (Phone)                                           Server
======================================================================================
1. Player changes system date to TOMORROW (+24 hrs).
   Plays 1 level (Level 50 -> 51).
   SaveSystem.Save() records saved_at = T_future (Now + 24h).
   Uploads to server ─────────────────────────────────────────> Server compares:
                                                                T_future > stored_at (TRUE)
                                                                Stores Level 51, saved_at = T_future.
2. Player changes system date BACK to normal time.
3. Player plays levels 52, 53, 54 on the bus (OFFLINE).
   SaveSystem.Save() records saved_at = T_bus (Now + 2h).
   Local save on disk holds Level 54, saved_at = T_bus.
   CloudSync queues uploads in offline buffer.
4. Player arrives home and connects to Wi-Fi.
   Queued upload sent to server:
   (Level 54, saved_at = T_bus) ──────────────────────────────> Server compares:
                                                                Incoming saved_at (T_bus) vs
                                                                Stored saved_at (T_future)
                                                                Since T_bus < T_future:
                                                                REJECTS upload!
                                                                Per Fact 3, sends stored save back:
                                <────────────────────────────── (Level 51, saved_at = T_future)

   OnCloudSave(serverJson) executes.

   Evaluates to TRUE!

```

#### Step-by-Step Technical Breakdown:
1. **Future Clock Spoofing**: The player advances their phone clock by +24 hours to bypass a cooldown gate. They beat level 51. `SaveSystem.Save()` executes:
   ```csharp
   Current.saved_at = DateTimeOffset.Now.ToUnixTimeSeconds(); // T_future = T_0 + 86400s
   ```
   The phone uploads this save. The server compares $T_{future} > T_{stored}$, accepts it, and commits $T_{future}$ as the authoritative player timestamp.
2. **Clock Restoration**: The player restores the phone clock to real-world time ($T_0 + 600s$).
3. **Offline Play on Bus**: On the bus without internet, the player clears levels 52, 53, and 54. After level 54, `SaveSystem.Save()` executes using the restored clock:
   ```csharp
   Current.saved_at = T_bus; // T_bus = T_0 + 7200s
   ```
   Notice that $T_{bus}$ is **22 hours in the past** relative to $T_{future}$ ($T_{bus} < T_{future}$). The local disk holds Level 54, and `CloudSync` buffers the upload.
4. **Server Rejection on Reconnection**: When the player reaches home and connects to Wi-Fi, the buffered save (`level: 54, saved_at: T_bus`) uploads to the server. The server evaluates:
   $$\text{incoming } saved\_at \,(T_{bus}) > \text{stored } saved\_at \,(T_{future}) \implies \text{FALSE}$$
   The server refuses to keep the upload.
5. **Reversion Echo**: Per Fact 3, bullet 2: *"If the server does not keep it, it sends its stored save back to the device that uploaded. On the device, both arrive through OnCloudSave."* The server echoes back the stored save (`level: 51, saved_at: T_future`).
6. **Local State Wiped**: The phone receives the echoed server save in `SaveSystem.OnCloudSave`. It executes:
   ```csharp
   if (server.saved_at > Current.saved_at) // T_future > T_bus (TRUE)
   {
       Current = server; // Overwrites Level 54 with Level 51!
       File.WriteAllText(LocalPath, serverJson);
   }
   ```
   The player's legitimate bus gameplay is destroyed.

#### Step-by-Step Technical Breakdown:
1. **Entitlement Purchase (Phone, March)**: The player purchases the "No Ads" IAP on their phone. `Current.no_ads = true; Current.saved_at = T_{march};`. The save is committed to the server.
2. **Dormant Device (Old Tablet)**: The tablet remained powered off or disconnected since February ($T_{feb} < T_{march}$). Its local JSON file contains `"no_ads": false`.
3. **Stale Device Activation (Last Week)**: The player opens the game on the old tablet without an active internet handshake (or before sync completes). `SaveSystem.Load()` reads the old file. The player clears one level.
4. **Timestamp Promotion of Obsolete State**: Finishing that level triggers `SaveSystem.Save()`. The tablet updates its timestamp:
   ```csharp
   Current.saved_at = DateTimeOffset.Now.ToUnixTimeSeconds(); // T_lastweek
   ```
   Notice: `Current.no_ads` on the tablet is **still `false`**, but its timestamp is now $T_{lastweek}$, which is months ahead of $T_{march}$ ($T_{lastweek} \gg T_{march}$).
5. **Server Overwrites Entitlement**: The tablet uploads its save to the server. The server compares timestamps: $T_{lastweek} > T_{march}$. Because the server is a blind blob store that does not inspect fields, it replaces the player's account save with the tablet's blob (`no_ads = false`).
6. **Phone Poisoned**: When the player returns to their phone, the phone syncs with the server. Since the server's timestamp ($T_{lastweek}$) is newer than the phone's March timestamp, the phone accepts the server payload. The paid entitlement is wiped, violating the primary rule: *"no player may lose anything that they paid for."*

# Task 3: System Design for Version 2.5

To satisfy the Invariable Rule, eliminate all three support failure modes, and decouple `coins` from `gems`, we must abandon the "dumb blob server + client clock LWW" architecture.

### Architectural Principles (SOLID):
1. **Single Responsibility Principle (SRP)**: Segregate save serialization, local persistence, cloud transmission, conflict resolution, and wallet balance management into distinct classes instead of a single static `SaveSystem`.
2. **Open/Closed Principle (OCP)**: Schema migration must allow adding new fields (`gems`, `schema_version`, `revision`) without breaking deserialization of older schemas.
3. **Liskov Substitution Principle (LSP)**: Conflict resolution strategies must implement a uniform interface (`IConflictResolutionStrategy`) that guarantees invariant preservation across offline, multi-device, and migration scenarios.
4. **Interface Segregation Principle (ISP)**: Separate read-only game state queries (`IPlayerProgressReader`) from write/mutation pipelines (`IPlayerProgressWriter`) and sync management (`ICloudSyncService`).
5. **Dependency Inversion Principle (DIP)**: Game gameplay loops depend on abstract interfaces, allowing testability, mocking, and headless validation.

### 3.2 Authoritative Conflict-Free Resolution Rules (CRDT & Monotonicity)

Instead of Last-Write-Wins on client timestamps, both client and server adopt **domain-specific monotonic merge rules**:

| Domain Field | Merge Strategy | Formal Rule | Rationale |
| :--- | :--- | :--- | :--- |
| **Level** | Monotonic Maximum | $\text{Level}_{merged} = \max(\text{Level}_{local}, \text{Level}_{remote})$ | A player never loses beaten puzzle levels (Resolves Incident 1 & 2). |
| **No-Ads** | Logical OR (Sticky True) | $\text{NoAds}_{merged} = \text{NoAds}_{local} \lor \text{NoAds}_{remote} \lor \text{ServerReceiptValid}$ | Once unlocked or purchased, an entitlement can never be unset by a stale device (Resolves Incident 3). |
| **Inventory** | Item-wise Maximum or Ledger Delta | $\text{Inv}[item]_{merged} = \max(\text{Inv}[item]_{local}, \text{Inv}[item]_{remote})$ | Prevents loss of earned/bought consumables. |
| **Gems** (Hard) | Server Authoritative Ledger | Managed via Server Ledger Transactions | Gems can only be credited by verified IAP receipts and debited by verified server-validated store purchases. |
| **Coins** (Soft) | Monotonic Revision Vector + Delta Merge | $\text{Coins}_{merged} = \text{Coins}_{base} + \Delta\text{Coins}_{local} + \Delta\text{Coins}_{remote}$ | Protects earned coins during offline play across devices. |
| **Ordering** | Monotonic Server Revision | $\text{Revision}_{server} = \text{Revision}_{stored} + 1$ | Client clock is completely discarded for ordering. Server assigns sequential revisions. |

### 3.3 What the App Does (Client Architecture - Python / Java SOLID Implementation)

Here is the complete SOLID-compliant implementation for Version 2.5 (implemented in Python with direct Java object-model parity):

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import Dict, Any, Optional, Callable
import os
import json
import time

# ============================================================================
# 1. DATA MODELS & SCHEMAS (Open/Closed Principle - OCP)
# ============================================================================

@dataclass
class InventoryData:
    hammer: int = 0
    shuffle: int = 0

    def to_dict(self) -> Dict[str, int]:
        return {"hammer": self.hammer, "shuffle": self.shuffle}

@dataclass
class WalletData:
    coins: int = 0  # Soft currency: earned exclusively through gameplay
    gems: int = 0   # Hard currency: bought with real money only

    def to_dict(self) -> Dict[str, int]:
        return {"coins": self.coins, "gems": self.gems}

@dataclass
class EntitlementsData:
    no_ads: bool = False  # Durable entitlement: sticky-true once unlocked

    def to_dict(self) -> Dict[str, bool]:
        return {"no_ads": self.no_ads}

@dataclass
class SaveDataV2:
    player_id: str
    schema_version: int = 2
    revision: int = 0              # Monotonically increasing sequence from server
    client_saved_at: int = 0       # Informational client timestamp
    device_id: str = "device_client"
    level: int = 1
    wallet: WalletData = field(default_factory=WalletData)
    inventory: InventoryData = field(default_factory=InventoryData)
    entitlements: EntitlementsData = field(default_factory=EntitlementsData)

    # Legacy mirror properties for backward-compatibility with older parsers
    @property
    def coins(self) -> int:
        return self.wallet.coins

    @coins.setter
    def coins(self, val: int):
        self.wallet.coins = int(val)

    @property
    def no_ads(self) -> bool:
        return self.entitlements.no_ads

    @no_ads.setter
    def no_ads(self, val: bool):
        self.entitlements.no_ads = bool(val)

    def to_dict(self) -> Dict[str, Any]:
        return {
            "schema_version": self.schema_version,
            "player_id": self.player_id,
            "device_id": self.device_id,
            "revision": self.revision,
            "client_saved_at": self.client_saved_at,
            "level": self.level,
            "wallet": self.wallet.to_dict(),
            "inventory": self.inventory.to_dict(),
            "entitlements": self.entitlements.to_dict(),
            "coins": self.wallet.coins,
            "no_ads": self.entitlements.no_ads
        }

# ============================================================================
# 2. INTERFACES (Interface Segregation & Dependency Inversion - ISP & DIP)
# ============================================================================

class ISaveStorage(ABC):
    @abstractmethod
    def load(self) -> Optional[SaveDataV2]: pass
    @abstractmethod
    def save(self, data: SaveDataV2) -> None: pass

class IConflictResolver(ABC):
    @abstractmethod
    def resolve(self, local: SaveDataV2, incoming: SaveDataV2) -> SaveDataV2: pass

class ICloudSyncClient(ABC):
    @abstractmethod
    def upload(self, data: SaveDataV2, on_success: Callable[[SaveDataV2], None], on_failure: Callable[[str], None]) -> None: pass

class ITimeProvider(ABC):
    @abstractmethod
    def get_current_unix_time(self) -> int: pass

# ============================================================================
# 3. CORE DOMAIN IMPLEMENTATIONS (Single Responsibility & Liskov Substitution)
# ============================================================================

class DomainMonotonicConflictResolver(IConflictResolver):
    """
    CRDT-inspired Monotonic Conflict Resolver.
    Invariant: 'No player may lose progress, or anything that they paid for.'
    """
    def __init__(self, time_provider: ITimeProvider):
        self.time_provider = time_provider

    def resolve(self, local: SaveDataV2, incoming: SaveDataV2) -> SaveDataV2:
        if incoming is None: return local
        if local is None: return incoming

        # Monotonic merges:
        # Rule 1: Level can NEVER regress (Resolves Support Incidents 1 and 2)
        resolved_level = max(local.level, incoming.level)

        # Rule 2: Entitlements are sticky-true (Resolves Support Incident 3)
        resolved_no_ads = local.entitlements.no_ads or incoming.entitlements.no_ads

        # Rule 3: Consumables never drop
        resolved_inventory = InventoryData(
            hammer=max(local.inventory.hammer, incoming.inventory.hammer),
            shuffle=max(local.inventory.shuffle, incoming.inventory.shuffle)
        )

        # Rule 4: Wallet protection
        resolved_wallet = WalletData(
            coins=max(local.wallet.coins, incoming.wallet.coins),
            gems=max(local.wallet.gems, incoming.wallet.gems)
        )

        return SaveDataV2(
            player_id=local.player_id,
            schema_version=2,
            revision=max(local.revision, incoming.revision),
            client_saved_at=self.time_provider.get_current_unix_time(),
            device_id=local.device_id,
            level=resolved_level,
            wallet=resolved_wallet,
            inventory=resolved_inventory,
            entitlements=EntitlementsData(no_ads=resolved_no_ads)
        )

class SaveManager:
    """
    High-level lifecycle coordinator replacing the static SaveSystem.
    Depends exclusively on abstractions (DIP).
    """
    def __init__(self, storage: ISaveStorage, resolver: IConflictResolver, cloud_client: ICloudSyncClient, time_provider: ITimeProvider):
        self.storage = storage
        self.resolver = resolver
        self.cloud_client = cloud_client
        self.time_provider = time_provider
        self.current: Optional[SaveDataV2] = None

    def initialize(self, default_player_id: str) -> SaveDataV2:
        self.current = self.storage.load()
        if self.current is None:
            self.current = SaveDataV2(player_id=default_player_id)
            self.storage.save(self.current)
        return self.current

    def commit_save(self) -> None:
        if not self.current: return
        self.current.client_saved_at = self.time_provider.get_current_unix_time()
        self.storage.save(self.current)
        self.cloud_client.upload(self.current, 
            on_success=lambda ack: self._on_cloud_ack(ack), 
            on_failure=lambda err: None)

    def _on_cloud_ack(self, ack: SaveDataV2):
        if ack:
            self.current.revision = max(self.current.revision, ack.revision)
            self.storage.save(self.current)

    def apply_cloud_save(self, incoming: SaveDataV2) -> SaveDataV2:
        self.current = self.resolver.resolve(self.current, incoming)
        self.storage.save(self.current)
        return self.current
```

### 3.4 What the Server Does (Backend Architecture)

The server transitions from a passive JSON relay to an **Active Transactional Coordinator**:

1. **Monotonic Revision Sequence**:
   * Every player account maintains a `current_revision` (integer).
   * When an upload is received, the server checks `upload.revision`.
   * If `upload.revision == current_revision`, the server increments `revision = current_revision + 1`, merges fields using monotonic rules, and writes atomically to database storage.
   * If `upload.revision < current_revision` (concurrent edit or delayed offline queue), the server performs a **Three-Way Merge** between `Database_State`, `Upload_State`, and the `Base_State`, or applies domain merge rules (`Max(Level)`, `Union(Inventory)`, `Sticky(NoAds)`).
2. **Authoritative Gem Ledger**:
   * Gems can only be minted via Apple App Store / Google Play verified server-to-server webhook receipts (`/api/v1/iap/verify`).
   * When the store sells an item for gems, the client requests a transactional purchase: `POST /api/v1/store/buy { item: "hammer", cost_gems: 50 }`. The server validates the player's gem balance, deducts gems, increments the inventory item, and increments the account revision.
3. **Legacy Adapter Layer (Handling v2.0 - v2.4 Clients)**:
   * When an older client uploads save JSON, the server's Ingestion Gateway parses it using the legacy schema.
   * The server updates `level = Max(server.level, legacy.level)` and `inventory`.
   * **Crucial Rule**: The server **never** overwrites `gems` or unsets `no_ads` from an incoming legacy client upload!
   * When an older client queries the server, the server projects its database state into the legacy JSON schema (`{"player_id": "...", "coins": server.coins, "level": server.level, ...}`), ensuring older clients never break.

# Task 4: Splitting Existing Coins into Coins and Gems

### 4.1 The Business & Mathematical Problem
* **Facts**:
  * Prior to v2.5: Players earned coins via gameplay AND purchased coin packs with real money (Fact 1 & 2).
  * In v2.5: Coins are earned by playing only. Gems are bought with real money only. The store will sell items for gems (Assignment Brief, Page 2).
  * Fact 4: *"The server has a record of each coin pack that a player bought: player, pack, number of coins, time. The server has no record of how players spent coins. Coins are spent on the phone."*
  * The Invariable Rule: *"No player may lose progress, or anything that they paid for."*

If a player bought 10,000 coins for $20 to buy powerups in the store, and in v2.5 the store no longer accepts coins (it sells items for gems), leaving their purchased coins as soft "coins" completely strips them of their paid purchasing power! Conversely, if we turn all coins into gems, F2P players who ground 100,000 coins get hundreds of dollars in hard currency for free, destroying future IAP monetization.

---

### 4.2 Candidate Split Rules & Trade-Off Evaluation

We analyze three alternative split algorithms against our invariants:

```
+--------------------------------------------------------------------------------------------------+
| Split Options Comparison                                                                         |
+--------------------------+-----------------------+-----------------------+-----------------------+
| Criterion                | Option 1: Pro-Rata    | Option 2: FIFO Ledger | Option 3: Full Grant  |
|                          | Historical Ratio      | Replay (Selected)     | (Double Up)           |
+--------------------------+-----------------------+-----------------------+-----------------------+
| Protects Payer Value?    | Partial (Payers lose  | YES (100% of unspent  | YES (Generous, but    |
|                          | unspent bought coins) | paid coins -> gems)   | causes hyperinflation)|
| Exploitable by F2P?      | No                    | No (F2P gets 0 gems)  | Yes (Huge F2P grants) |
| Financial Liability Risk | Moderate              | Zero unearned debt    | Extreme deferred cost |
| Implementation Burden    | Medium                | Low & Deterministic   | Very Low              |
+--------------------------+-----------------------+-----------------------+-----------------------+
```

---

### 4.3 The Chosen Rule: "FIFO Payer-Protection Ledger Split"

#### Mathematical Formulation:
For each player account upon migrating to v2.5:
1. Query the server's purchase ledger (Fact 4) to compute total lifetime purchased coins:
   $$C_{purchased} = \sum \text{pack.coins}$$
2. Read the player's current coin balance at migration:
   $$C_{current}$$
3. **Payer-Protection Principle**: Under the most player-favorable accounting principle ("players spend free earned coins first before touching paid coins"):
   * Unspent paid coins eligible for gem conversion:
     $$PaidCoins = \min(C_{current}, C_{purchased})$$
   * Remaining gameplay-earned coins:
     $$EarnedCoins = C_{current} - PaidCoins$$
4. Convert $PaidCoins$ into $Gems$ at the official store economic parity rate $R_{store}$ (e.g., if 100 coins in old store bought 1 hammer, and 10 gems in new store buys 1 hammer, then $R_{store} = 0.1 \text{ gems/coin}$):
   $$\text{Gems}_{new} = \text{Round}\big(PaidCoins \times R_{store}\big)$$
   $$\text{Coins}_{new} = EarnedCoins$$

> **Exception Safeguard (The Zero-Coin Payer Floor)**:
> If a player bought coin packs ($C_{purchased} > 0$) but currently has $C_{current} == 0$ (they spent every single coin already), they have not lost coins, because they consumed what they bought. However, to celebrate the update and prevent support friction, we grant a flat goodwill grant of 50 Gems to any historical purchaser.

### 4.4 Walkthrough on Two Concrete Example Players

Assume an economic conversion rate of **1 Gem per 10 Coins** ($R_{store} = 0.1$):

#### Player 1: "The Hardcore Free-to-Play Grinder"
* **Profile**: Level 180, has never spent real money ($C_{purchased} = 0$).
* **Current Balance at Migration**: $C_{current} = 8,400 \text{ coins}$.
* **Execution of Rule**:
  * $PaidCoins = \min(8400, 0) = 0$
  * $EarnedCoins = 8400 - 0 = 8,400$
  * $\text{Gems}_{new} = 0$
  * $\text{Coins}_{new} = 8,400$
* **Outcome**:
  * **Who Gains**: Player retains 100% of their earned coins ($8,400$) to use in gameplay (continues, board shuffles, future coin sinks).
  * **Who Loses**: Player receives 0 gems. They cannot buy store items directly until they earn gems or purchase them.
  * **Cost to Company**: **$0.00**. No artificial hard currency liability is created.

#### Player 2: "The Paying Supporter / Hoarder"
* **Profile**: Level 45. Bought two $10 coin packs ($2 \times 2,500 = 5,000 \text{ coins total}$, $C_{purchased} = 5,000$).
* **Current Balance at Migration**: Has spent 1,200 coins on boosters; current balance $C_{current} = 3,800 \text{ coins}$.
* **Execution of Rule**:
  * $PaidCoins = \min(3800, 5000) = 3,800$
  * $EarnedCoins = 3800 - 3800 = 0$
  * $\text{Gems}_{new} = 3,800 \times 0.1 = 380 \text{ gems}$
  * $\text{Coins}_{new} = 0 \text{ coins}$ + a migration bonus of $500 \text{ gameplay coins}$ granted by the studio so they can still play level continues.
* **Outcome**:
  * **Who Gains**: Player receives 380 gems—exactly preserving the store purchasing power of the $3,800$ unspent coins they paid real money for! They lose nothing they paid for.
  * **Who Loses**: Their coin balance is converted to gems, but compensated with a small coin starter bonus.
  * **Cost to Company**:
    * **Accounting**: Reclassifies deferred revenue on Finance's balance sheet from unspent coin obligations to unspent gem obligations. Zero cash outlay.
    * **Opportunity Cost**: The player has 380 gems to spend in the new store, deferring their next IAP by ~2 weeks.

Given Fact 5 (store reviews take 3-7 days, 18% churn on forced updates, and Android 7 users cannot update), a blunt "maintenance window and force-update" will devastate the player base. We execute a **Zero-Downtime, Staged Compatibility Rollout**.

   +------------------------+      +------------------------+     +------------------------+
               │                               │                              │
               ▼                               ▼                              ▼
          Gate Check 0                    Gate Check 1                   Gate Check 2

### Step 1: Deploy Server-Side Ingestion & Backward Compatibility Layer
* **Action**: Update server API to handle both legacy payloads (`SaveData v1`) and new schemas (`SaveData v2`). Deploy the monotonic merge engine.
* **Pre-Step Check**: Run regression test suite replaying historical support saves (including Incidents 1, 2, and 3). Verify that legacy clients uploading `SaveData` receive valid responses without dropping existing fields.
* **Failure Detection**: Spike in `5xx` errors or unhandled JSON deserialization exceptions on the sync endpoint.
* **Undo / Rollback**: Instant blue/green container traffic shift back to the legacy server build.

---

### Step 2: Server Shadow Migration Run (Dark Launch)
* **Action**: As legacy clients upload saves, the server runs the Currency Split Algorithm in **shadow mode** (calculating and logging $PaidCoins$, $EarnedCoins$, and $Gems$ in audit tables without modifying the player's live save).
* **Pre-Step Check**: Audit log shows that $PaidCoins \le C_{purchased}$ across 100% of inspected accounts.
* **Failure Detection**: Any logged account generating negative gems, or discrepancies where $PaidCoins > C_{purchased}$.
* **Undo / Rollback**: Feature flag `SHADOW_SPLIT_AUDIT = false`.

---

### Step 3: Client Canary Release (1% Staged Rollout on Google Play & App Store)
* **Action**: Release client v2.5 to 1% of the active install base. Version 2.5 executes the split upon first boot, acknowledged by the server.
* **Pre-Step Check**: Store approval received; backend canary instances healthy.
* **Failure Detection**:
  * Crash rate > 0.1% on Crashlytics/Sentry.
  * Currency drift alerts (mismatch between client reported gems and server ledger).
  * Spike in support tickets with keywords "lost levels", "lost coins", "ads".
* **Undo / Rollback**:
  * Halt staged rollout in Google Play Console / Apple App Store Connect immediately.
  * Server detects v2.5 clients and activates remote config kill-switch `DISABLE_GEM_STORE = true`, reverting store purchases to server-managed fallback.

---

### Step 4: Staged Rollout Expansion (10% $\rightarrow$ 25% $\rightarrow$ 50% $\rightarrow$ 100%)
* **Action**: Expand rollout over 7 days in alignment with store rollout dynamics (Fact 5, bullet 2).
* **Pre-Step Check**: Support ticket volume at canary stage is normal; no data loss tickets.
* **Monitoring Alarms**:
  * Real-time Datadog/CloudWatch metric: `sync.conflict.level_regressions` (must be exactly 0).
  * Telemetry metric: `ledger.gem_mint_anomaly` (triggers if gem creation exceeds expected purchase conversions).
* **Undo / Rollback**: Pause rollout percentage. Deploy server-side compensatory grant script.

---

### Step 5: Perpetual Support for Legacy & Android 7 Players
* **Action**: Because 5% of players are on Android 7 and cannot update, keep the Server Legacy Adapter online indefinitely.
* **Policy**: When Android 7 users purchase coin packs, their purchases are recorded in Fact 4's ledger. If they ever transfer to a modern device on v2.5, their coin packs will immediately convert to gems upon first login.

# Task 6: System Boundaries & Cross-Functional Alignment

### 6.1 Where the Design Can Still Fail (Edge Cases & Boundaries)

1. **Cross-Version Concurrent Multi-Device Thrashing**:
   * *Edge Case*: A player opens v2.5 on their new Android 14 phone and v2.2 on their old Android 7 tablet simultaneously. On the tablet, they spend 1,000 old coins on continues. On the phone, those same 1,000 coins were already converted into 100 gems!
   * *Mitigation*: The server detects that the account has completed v2.5 migration. When the legacy v2.2 tablet tries to spend coins, the server rejects the sync or clamps the tablet's coin balance to 0, flagging a one-time in-game dialogue on the tablet: *"Account upgraded on another device. Please continue on your updated device."*
2. **Prolonged Offline Play Across Currency Boundaries**:
   * *Edge Case*: A player goes into offline flight mode on v2.4 with 5,000 coins. On the web portal or another device, they migrate to v2.5. Two weeks later, the offline v2.4 reconnects.
   * *Mitigation*: The server's monotonic merge engine treats the migration event as a tombstone. Incoming legacy offline diffs are merged for level progression, but currency balances are deferred to manual support review if a collision is detected.
3. **Refunds on Grandfathered Coin Packs**:
   * *Edge Case*: A player bought a coin pack 30 days ago, migrates to v2.5 receiving 200 gems, spends the 200 gems on store items, and then requests a credit card chargeback / Google Play refund for the original coin pack.
   * *Mitigation*: Server-side purchase ledger tracks receipt IDs tied to gem conversions. On refund webhook, gem balance is deducted; if negative, account is flagged for negative balance resolution.

### 6.2 Targeted Questions for Product Management & Finance

#### For Finance:
1. **ASC 606 Revenue Recognition & Breakage**: How does Finance plan to recognize revenue for grandfathered unspent coins converted into gems? Should unspent converted gems be classified as deferred revenue liabilities until consumed, or recognized based on historical breakage curves?
2. **Exchange Parity & Fractional Currencies**: When converting $PaidCoins$ to gems, what rounding policy is approved for fractional gems? (e.g., if a player has 15 paid coins at a 1:10 ratio = 1.5 gems, do we round up to 2 gems to prevent compliance complaints, or round to nearest?)
3. **Refund Accounting**: In the event of an IAP refund for a coin pack purchased in v2.4, is Finance prepared to claw back gems in v2.5, or write off the loss to preserve player LTV?

#### For Product Management:
1. **Soft Currency (Coins) Sinks in v2.5**: Now that coins are earned solely by playing and store items (hammers, shuffles) cost gems, what sinks remain for coins? (e.g., level retries, cosmetic tiles, card packs?) If coins accumulate without sinks, players will hoard millions, causing perceived currency uselessness.
2. **Android 7 Sunsetting Roadmap**: Given that ~5% of players cannot update to v2.5, what is our target end-of-life (EOL) date for legacy client support? Can we offer a lightweight web-version / cloud-save export for these users to migrate to a new device?
3. **Pricing Parity in Store**: What is the exact price tier mapping for items? If a hammer cost 100 coins in v2.4 ($1.00 value), will it cost 10 gems in v2.5, and does the smallest gem pack cost $0.99 for 10 gems? Consistency here is critical to avoid player backlash.
